# Offline RC alpha screen diagnostics

Run the standalone screen against an authorized copy of the exact original
packet, with a new output path:

```sh
python3 scripts/screen_rc_line_search_alpha.py PACKET_ROOT NEW_REPORT.json
```

This POSIX-only reader retains no-follow directory/file handles, original-byte
inventory binding, frozen source identity, bounded alpha trial prefixes, and
whole-group training isolation. It does not execute a solver, read reserved
cases, recover missing outcomes, or promote scientific/readiness claims.

## Output and compatibility

The report remains `rc-line-search-alpha-offline-screen.v1`. Its existing
status, issues, rows, hashes of consumed sources, decision gates, and work
boundaries keep their meanings. Additive `fold_issues[].failures` entries attach
stable codes and applicable `target_index`, one-based `ordinal`, or `count`.
The original human-readable `issues` strings remain available.

The additive `diagnostics` object has its own
`rc-line-search-alpha-screen-diagnostics.v1` version. It is included in the
report self-hash; reports generated by this version therefore have different
report hashes even when the source packet is identical. Consumers should verify
the entire emitted report rather than carrying forward an older report hash.

`diagnostics.classification` describes the existing outcome:

- `blocked_original_evidence`: original work or repeat identity is unverified
- `false_skip_gate_failed`: a completed screen observed false skips
- `insufficient_group_support`: a completed screen lacks the required group support
- `offline_design_support_only`: the existing offline gate supports designing an
  online experiment; it does not validate online outcomes or measured savings

`diagnostics.failure_counts` counts failure records by code, not unique targets
or folds. One target can contribute multiple failure records. The codes are
`unattempted_targets`, `missing_invocation`, `multiple_invocations`,
`unknown_work`, `nonreturned_invocation`, `noncommitted_invocation`,
`unverified_trial_history`, `incomplete_physical_work_comparison`, and
`repeat_identity_mismatch`. An `unattempted_targets` record is one failure record
with a separate missing-target `count`; repeat identity counts mismatching
case/ridge/repetition combinations. Empty counts do not imply experimental
eligibility: read the classification and original decision together.

## CLI behavior

- Completed and blocked reports retain exit status 0 and the existing stdout
  JSON fields, with `diagnostics` added. Check `status` and `screen_decision`;
  exit status 0 alone is not a passing scientific gate
- A short human-readable summary and work-proxy boundary are written to stderr
- A `TraceError` rejects input with exit status 2 and a stdout JSON object
  containing `status: rejected_input`, `failure_code`, `summary`, and
  `solver_calls: 0`. No report, output directory, or screen decision is created
- Input rejection codes are `unsafe_or_missing_input`,
  `inventory_identity_failed`, `undeclared_input`, `content_binding_failed`,
  `invalid_json`, and the general `trace_validation_failed`. This is a
  diagnostic taxonomy, not relaxed admission or a repair mechanism
- Output is still created exclusively. Existing reports are never overwritten
- Rejection summaries use fixed text and do not echo raw input or exception messages
- Unexpected programming errors and output I/O errors are not converted into
  scientific rejection reports

## Focused verification

```sh
python3 -m pytest -q tests/test_rc_line_search_alpha_screen.py
python3 -m ruff check scripts/screen_rc_line_search_alpha.py tests/test_rc_line_search_alpha_screen.py
```

The tests use synthetic records. They preserve source bindings in those
fixtures, exercise all blocked-fold codes, reject linked/FIFO/traversal inputs,
check strict JSON failures and exclusive output, and retain unknown labels at
the full alpha-prefix boundary. They do not execute or certify the historical
packet, run new solver experiments, or produce readiness evidence.
