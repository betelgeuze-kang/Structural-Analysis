# Bind reference execution to the pinned OpenSees payload

Source `441ac7b415e491f56ca7dba04243d713d35ce13f` connects the verified wheel
assets to the modules actually executed by both technical-reference entry points.
The preceding arithmetic diagnosis exposed why this connection is necessary:
checking wheel hashes and runtime version separately does not prove that the
supplied Python path contains those wheel bytes.

## Reproduced boundary and implementation

A local copy of the pinned package tree has only its native extension replaced
by the [previous arithmetic-modified build](opensees-corot2d-arithmetic-20260910.md).
The unchanged pre-fix embedded driver runs successfully, reports 3.7.1 and
completes 35 analyze calls. Its output satisfies the old process/output/version
checks. No misleading official receipt is generated by this probe.

The new `scripts/pinned_opensees_runtime.py` performs the following operations:

1. Verify the exact two wheel names, hashes and complete 24-member manifest.
2. Compare the supplied runtime code/data with the pinned wheel members. A
   modified extension or symlink is rejected before launching a child. Installed
   dist-info metadata may differ; execution takes metadata from the original wheel.
3. Extract only verified archive members into a private temporary directory.
   Extra modules or bytecode at the supplied path cannot enter that execution.
4. Run Python with `-I -S -B`, a private working directory and no inherited dynamic
   loader path/preload overrides. This is import reproducibility, not a security
   sandbox or independent operator attestation.
5. Verify all staged members before and after the driver, and verify the actual
   origins of `openseespy`, its API module, `openseespylinux` and the native module.
6. Return a portable hash-bound provenance object in the execution outputs. The
   parent checks its exact expected content and removes the private extraction.

The code-to-code and modal/buckling receipt builders both pass their verified
wheel inputs through this helper. Both schemas accept only the exact pinned
binding. Source manifests include the helper and member policy JSON. New fresh
receipts using that source set must contain the binding. Historical receipts
remain readable without inventing a binding or a new external execution; the
existing replay/freshness and independent-validation boundaries remain in force.

## Actual runtime checks

After the implementation commit, both current entry points execute the official
pinned wheels. The complete code-to-code numerical payload equals the earlier
pinned-runtime payload exactly after removing per-attempt timing telemetry.
All 35 analyze calls return zero. Its two known reaction comparison failures
remain; this change does not repair the official wheel's arithmetic.

The modal entry point also executes successfully. A separate exact-rational
calculation checks its two-free-DOF cantilever eigenpairs against the analytical
stiffness and consistent-mass matrices. The largest relative eigenpair residual
is `1.5005303038608907e-14`; mass orthogonality normalized by the two modal norms
is `2.1559890340707695e-15`. Raw eigenvectors are retained. An initial audit
incorrectly assumed unit modal mass and failed; its source and observed Gram
matrix are preserved. Correcting that scale assumption requires no extra
eigenanalysis and does not modify the computed vectors.

Both entry points reject the arithmetic-modified native extension before any
subprocess launch. Thus a successful modified build cannot silently inherit the
official wheel's identity through these entry points.

This observation includes 35 pre-fix modified-driver and 35 post-fix official
analyze calls, plus the separate post-fix modal eigenanalysis. There are no new
product or CalculiX analyses, complete receipt generations, learning fits or
protected receipt rewrites. The initial/full drivers also contain their existing
modal query; analyze-call counts are not counts of every numerical operation.
